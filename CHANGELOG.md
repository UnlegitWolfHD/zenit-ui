## [Unreleased]

### Added

- **`live` on toasts and `provideZenitToast({ maxVisible, overflow })`.** An application whose own toast service announced warnings as urgently as errors can now say so per toast: `live: 'assertive'` puts it into the `role="alert"` region of `z-toast-outlet`, `'polite'` into the `role="status"` one; without it `danger` stays assertive and the other four polite, as before, and `ZToastItem` carries the resolved value as the optional field `live`. `provideZenitToast` sets how many toasts are visible (`maxVisible`, default 3) and what a toast does while every place is taken: `'replace'` (default) closes the oldest toast that is not standing, `'queue'` never closes one and lets the new toast wait. A waiting toast is not in `toasts`, its duration starts only when it becomes visible, `dismiss(id)` takes it out of the queue and `dismiss()` empties it. The default stays `'replace'` because it is what every existing caller gets today and because the queue is a choice of the application, not a fix: a burst of confirmations that all wait their turn would still be read 15 seconds later. Documented in [`docs/components/toast.md`](docs/components/toast.md), "How many at a time"; tests in `toast.spec.ts` and `toast-outlet.spec.ts`. No demo, because neither changes anything visible on one page (`docs/abdeckung.md`).
- **Thumbnail of `z-row-main`: `thumbText`, `thumb`, `[zRowThumb]` and a fallback for a dead image.** A server list whose `title` is the server's own name and whose `image` is the game icon showed the initial of the server name when the icon was missing, and the browser's broken-image icon when its URL failed. `thumbText` names the text whose initial fills the thumbnail instead of `title` (empty keeps `title`), and an `image` that fires `error` drops into that initial the way the cover of `button[zGameTile]` drops into its text, through a `linkedSignal` on `image`, so a new URL is tried again. `[zRowThumb]` is a pure slot marker for an own medium in `.z-row__thumb`, an icon or an image, and replaces image and initial while it is rendered: a `contentChild` query decides, so a slot element inside an `@if` that is false leaves image or initial in place instead of an empty thumbnail. `thumb` (boolean, default `true`) set to `false` leaves the thumbnail out, for a list without one. No new class and no CSS rule; with none of the four set the row renders exactly as before. The image stays decorative with `alt=""`, so the game has to stand as text in the meta line too, as the guide says. No SSR risk: `(error)` is a template listener. Demo panel "Vorschaubild" on `/daten` (baselines `daten-1440` and `daten-375` re-recorded), tests in `rows.spec.ts`, documented in [`docs/components/server-list.md`](docs/components/server-list.md).
- **`tile` on `z-skeleton`.** A loading `z-game-grid` had no placeholder of the tile's shape: a line or a `thumb` jumps the grid when the tiles arrive. `<z-skeleton tile />` renders `z-skel--tile` with a 3:4 cover area and a title and a price line inside, the boxes of `.z-game` repeated with its `--space-2` gaps (addition to the reference, tokens and the literals of `.z-game__price` only), so it takes exactly the cell of a tile: measured in `e2e/zustaende.spec.ts` ("skeleton tile has the box of a game tile") at 1440 and 375px, 139.4 by 237.9px for both, cover included. The host stays `aria-hidden`; the grid carries `role="group"`, `aria-busy="true"` and an `aria-label`. Demo on `/werkzeuge` (baselines `werkzeuge-1440` and `werkzeuge-375` re-recorded for the new row), documented in [`docs/components/skeleton.md`](docs/components/skeleton.md) and [`docs/components/game-tile.md`](docs/components/game-tile.md).
- **`steppers` on `z-slider`.** `spec/components/Slider/README.md:12` requires plus and minus buttons "bei mehr als 12 Stufen oder auf Geräten ohne Maus"; the library had none, while a real consumer runs sliders with 15 to 29 steps. `steppers` adds two icon-only ghost buttons in size `sm` (`remove` and `add`) left and right of the track, as siblings of the range input, laid out in one grid row by the new host modifier `.z-range--steppers`; a slider without `steppers` carries neither, its markup is the one from before and it renders exactly as before. Each click moves the value to the next value on the step grid from `min`, clamped to `min` and to the last grid value that fits below `max` (0 to 10 in steps of 3 ends at 9, and ten presses from 0 to 1 in steps of 0.1 land on 1 exactly), so the element never corrects what a button wrote, and writes through the same path as the track, so model, `ControlValueAccessor`, Signal Forms and `valueChange` see exactly one change per click. Both are ordinary tab stops; at the end of the scale the button on that side takes `aria-disabled="true"` and a swallowed click instead of the native `disabled`, the way `z-pagination` already handles its arrows, so the focus stays where the user put it; a `disabled` slider disables both natively. Default `false` and never automatic: a slider that grows a pair of buttons the moment a `max` changes is a layout moving without anyone asking for it. Instead a development build prints one `console.warn` per slider, quoting the rule, when `(max - min) / step` is above twelve and `steppers` is off. The names come from the two new label keys `sliderDecrease` and `sliderIncrease` ("Verringern"/"Erhöhen", "Decrease"/"Increase"), with no input of their own, for the same reason `z-cost-chart` has none. Demo: `Aufbewahrung` (29 steps, locked through forms) and the new `Tickrate` (27 steps) on `/formulare`. Documented in [`docs/components/slider.md`](docs/components/slider.md) and [`docs/labels.md`](docs/labels.md).
- **`size` on `z-hero`.** `'xl'` or `'lg'`, default `'xl'`, so a sub-page can have the `display-lg` heading the design system asks for (`spec/components/Hero/README.md`: "`display-xl` nur auf der Startseite und auf /minecraft. Unterseiten nehmen `display-lg`", the same in `spec/guidelines/10-seitenmuster.md`). It was the only part of the Hero rule the API could not express; `display-lg` existed in `bundle.css` only inside the 640px block, where every hero drops into it. `'lg'` adds `z-hero--lg` on the host and nothing else, so the default renders byte for byte what it rendered before the input existed. The new rule takes the two values of that 640px block verbatim, which makes an `lg` hero at 1440px the same type as an `xl` hero at 639px: 40px/44px, `letter-spacing: -0.8px` (−0.02em), Space Grotesk 700, against 56px/60px/−1.12px for `xl`. Below 640px `lg` therefore stays `lg` while `xl` joins it, and the lead still drops from 20px to 16px in both. Independent of `headingLevel`, which says where the heading sits in the outline, not how big it is. Measured in `e2e/zustaende.spec.ts` ("Hero-Größen"), demonstrated by a second hero on `/werkzeuge` with the `/preise` text of the page pattern, documented in [`docs/components/hero.md`](docs/components/hero.md).
- **`button[zGameTile]` survives a cover that 404s.** `GameTile/README.md` defines the text fallback for a missing cover; a cover URL that fails to load used to leave the browser's broken-image icon in the 3:4 area instead. The `<img>` now carries `(error)`, which drops the tile into exactly that fallback — the title in the `display` face on the cover area — and emits the new output `(coverError)`, so an application can log the dead URL. The flag behind it is a `linkedSignal` on `cover`, so a new URL is tried again and the report fires once per URL. `alt=""` is unchanged, and so is everything a screen reader gets: the tile stays a toggle button with `aria-pressed`, and its accessible name stays title plus price, because the cover area is `aria-hidden` (see Fixed). No SSR risk: `(error)` is a template listener, nothing reads a browser global. Demo and baseline on `/werkzeuge` with `/covers/fehlt.jpg`, checks in `game-tile.spec.ts` and `e2e/zustaende.spec.ts`, documented in [`docs/components/game-tile.md`](docs/components/game-tile.md).
- **The page width is documented as an application setting.** `--container` stays at its default of 1120px in `tokens.css`; a product that wants a wider page writes `:root { --container: 1440px }` once in its own stylesheet, after `zenit-ui.css`, and every `.z-container` — header, `<main>` and footer of every page — follows. `:root`, not `html`: both weigh (0,1,0) so the later declaration wins, while an `html` selector at (0,0,1) would lose to `tokens.css` wherever it stood; the `styles` array of `angular.json` is that source order, the same fact `themes.css` already depends on. **No API was added.** An option on `provideZenitTheme` would have to write an inline style, and an inline style can never arrive earlier than the stylesheet that already carries the value: under a client-side render the page has no layout before Angular starts, under a prerender the value is in the render-blocking `<link>` of the same HTML, and in a static `index.html` Angular never runs — so, unlike a colour scheme, there is no stored user choice to read and no flash to prevent. `zenitThemeInitScript` and the `ng add` schematic are unchanged. An application that changes the width at runtime writes `document.documentElement.style.setProperty('--container', …)` itself, which beats every stylesheet. Measured at 1120, 1280, 1440 and 1600px over every demo page: nothing breaks, nothing hits a second `max-width`, and there is no horizontal scrolling at any width — the blocks that keep a width of their own are the sidebar (`--sidebar`), the configurator aside (340px), running text (`--measure`, 52ch, 40ch) and the overlays, each for a reason, and all of them are listed in the new section "Page width" of [`docs/layout.md`](docs/layout.md) next to the ones that grow. The reasoning and the measurement table are in [`docs/theming.md`](docs/theming.md), the gate is `e2e/breite.spec.ts`, and the demo header has a third control "Breite" (1120/1280/1440) that switches it live. That third control is the only reason 29 baselines of `ui-demo` were re-recorded: at 1440px the pages are pixel-identical outside rows 150 to 199, the strip the controls sit in, and at 375px the header wraps one row further, so every page moves down by exactly 72px and nothing else changes. No element screenshot of `e2e/zustaende.spec.ts` and no baseline of `beispiel-app` moved.
- **A server-rendering gate, `npm run check:ssr`.** `tools/check-ssr.mjs` prerenders every route of `beispiel-app` and of `ui-demo` in plain Node and fails on any render error; it runs inside `npm run check` after the two application builds and takes about 10 seconds for both. Both applications got the SSR setup of `ng add @angular/ssr` (`main.server.ts`, `app.config.server.ts`, `app.routes.server.ts` with `RenderMode.Prerender` for `**`) in a build configuration named `ssr` with `outputMode: 'static'`, so `ng serve`, the existing builds and the Playwright runs are untouched and no application source file changed. Without `provideClientHydration()`: the browser builds both applications ship never receive server markup, so it would do nothing there except warn (NG0505) on every dev start, and the server renders with or without it. Nothing else in this workspace renders on a server — the unit tests run in jsdom, which has `MutationObserver`, `ResizeObserver` and a layout, the Playwright suites run in a browser, and `check:bundle` only loads the package — so a component that reaches for a browser global while it is being constructed passed every check and still broke a consumer's SSR build. The gate checks the **output as well as the exit code**: the CLI fails a route that throws while rendering, but an error caught by Angular's error handler is only printed as `ERROR <Something>Error: …` while the route still counts as prerendered and the build reports success, so `ERROR`, `ReferenceError` and `is not defined` fail the gate on their own. Coverage is 76 of the 84 selectors; the eight that are missing and the limits of a gate that renders once without interaction are in `CONTRIBUTING.md`, the guarantee the library gives on a server in `projects/zenit-ui/README.md`. Dev dependencies `@angular/platform-server` and `@angular/ssr`, pinned to the workspace's Angular version; no `express` and no server entry, because a static prerender needs neither.
- **`z-combobox` searches on the server, waits and takes free text.** Six additive members, all of them off by default, so a combobox that says nothing new behaves byte for byte as before: `(queryChange)` reports the typed text and nothing the component writes itself; `filterLocally="false"` shows exactly the `options` it is given; `loading` draws one waiting row with a spinner under the options that are already there and sets `aria-busy`, without a "no match" row; `allowCustom` lets Enter, Tab and leaving the field commit the typed text and offers the same as a row `„<text>“ übernehmen` above the matches; `minQueryLength` holds the list back behind a hint row while still reporting the query; `selectedLabel` names a value whose entry the current answer no longer holds, while a value the field itself committed as free text is its own label until the caller changes either. The active row is now kept by its value instead of its index, so options replaced under an open panel move the keyboard along and `aria-activedescendant` never names a row that is gone. Text that is exactly the **label or the value** of an entry selects that entry instead of offering to make a second one, which is what a list keyed by ids needs; the own row is tracked by a key that no value can collide with. The status region counts matches only, never the action row. New label keys `comboboxLoading`, `comboboxUseCustom` and `comboboxMinQuery`. The three modes, the `resource()` recipe (with the `linkedSignal` that keeps the last answer while the next one loads — a loading resource falls back to its `defaultValue`, which would otherwise blank the panel on every keystroke), the RxJS recipe and the mapping from `mat-autocomplete` are in `docs/components/combobox.md`.
- **Theming.** The opt-in stylesheet `styles/themes.css` adds the colour schemes `light` and `contrast` next to the `dark` of `tokens.css`, plus the accents `blau`, `gruen` and `violett`. `provideZenitTheme()` applies the stored or the default choice before the first frame, `'system'` follows `prefers-color-scheme` live, and the service `ZTheme` switches scheme and accent, rejects unknown ids instead of throwing and writes nothing outside the browser. The values are derived by the contrast rules in `docs/theming.md` and checked by `node tools/check-theme-contrast.mjs` (3 schemes × 4 accents, 456 pairs, wired in as `npm run check:themes`); they still need the design owner's approval before they move into `tokens.json`.
- **Labels.** Every built-in text of the library lives in one registry: `Z_LABELS_DE` as the default, `Z_LABELS_EN` complete, `provideZenitLabels(partial)` to merge an override at bootstrap or on a lazy route, `Z_LABELS` for one subtree. The per-usage inputs still win. See `docs/labels.md`.
- **`ng add zenit-ui`.** A schematics collection that does the manual setup: style entries in `angular.json` (with `--themes` including `themes.css`), `z-root` on `<html>` and `<body>`, `@angular/cdk` and the four font packages with their `@import` rules, and `<z-toast-outlet />` in the root component. Idempotent, tested by `npm run test:schematics` against generated fixtures, built by `tools/build-schematics.mjs` as part of `npm run build:lib`. See `docs/ng-add.md`.
- **Signal Forms.** Every field of the library works with `[formField]` from `@angular/forms/signals` next to `ngModel` and reactive forms: `indeterminate` on the checkbox, `ariaDescribedby` on the fields, and the error text of `z-field` wired to the control. The demo page "Formulare" binds through Signal Forms first. The three ways to bind and when to pick which are in `docs/forms.md`.
- **Signal conventions.** `docs/signals.md` holds the rules this workspace follows (`input()`, `output()`, `computed()`, `linkedSignal()`, `resource()`, no effect for what a computed can do), an audit table over library and applications, and the places that deliberately deviate. The library tears down through `DestroyRef` instead of `ngOnDestroy`.
- **Row that is a link and carries actions.** `[zRowTitle]` and `a[zRowLink]` put the link on the title of a `div[zRow]`, where its stretched `::after` makes the whole row clickable with one tab stop and one focus ring, and `[zRowAction]` lifts the buttons of the row above that overlay. A `<button>` inside an `<a>` is invalid markup, so this is the way a row gets both a target and its own actions.
- **`[zRowMeta]`.** The meta line of a row as a slot instead of a string, so an address, a port or a file name inside it takes `z-mono` while the rest of the line stays in the body face, as CLAUDE.md asks.
- **`ZDialog.confirm({ restoreFocusTo })`.** Names the element that gets the focus when the dialog closes, as an `HTMLElement`, an `ElementRef` or a CSS selector. Set it when the element that opened the dialog is gone by then, a deleted row for example. A dialog opened from a menu item needs nothing: `ZDialog` finds the menu trigger by itself.
- **`headingLevel` on `z-hero`.** 1, 2 or 3, default 1, so a page that already owns an `<h1>` does not end up with two. The class and with it the type size stay the same on every level.
- **Example application `beispiel-app`.** One complete page, "Gameserver" of the customer area, as the template for real pages: shell with skip link, AppHeader, Footer and toast outlet; PageHeader with one fact and one primary; filter row as a Signal Form; panel "Meine Server" with ServerList, row link, row menu and Pagination; every state from `spec/guidelines/15-zustaende.md` reachable through `?zustand=laden|leer|fehler`, plus the filtered-to-nothing case; toast after a restart and a confirmation with the server name before deleting. It consumes the library from the built package in `dist/zenit-ui` through a `paths` override in its tsconfigs, following the setup steps of the package README, and thereby proves that the package works. Scripts `build:beispiel`, `start:beispiel` and `e2e:beispiel`; `check` and the CI workflow build and test it as well. Documentation in `projects/beispiel-app/README.md`.
- **The example application shows its own wiring.** Every region of the Gameserver page carries a disclosure ("So ist es eingebunden") with the source that produces it, and the page "Einbindung" (`/einbindung`) walks through the setup steps with the real files: `tsconfig` paths, the `styles` of `angular.json`, `index.html`, the font imports, the providers, the toast outlet and an own theme, plus the `ng add` shortcut. The blocks come from `tools/generate-example-snippets.mjs`, which copies the files verbatim into `quelltexte.generated.ts`; the regions are cut out at runtime by a tested pure function, and `npm run check:snippets` fails the build when the copy no longer matches the sources. New components `app-code-block` (mono, own scroll region, copy button with toast) and `app-theme-control` (scheme and accent from the header, stored by `ZTheme`).
- **Playwright suites.** The page checks (axe, no horizontal scrolling, computed-style rules, focus ring, touch targets) moved from `e2e/demo.spec.ts` into `e2e/pruefungen.ts`, unchanged, and are used by `e2e/beispiel.spec.ts` as well, which runs them in `dark`, `light` and `contrast` over both pages of the example application. Next to them: `e2e/zustaende.spec.ts` with an element screenshot per component state, `e2e/interaktion.spec.ts` for keyboard and overlay behaviour, `e2e/themes.spec.ts` over every scheme, and `e2e/a11y-baum.spec.ts` for landmarks and the heading outline.
- **Documentation.** One usage guide per building block under `docs/components/`, whose examples are checked against the real selectors, inputs and exports by `node tools/check-docs-examples.mjs`; `docs/migration-from-material.md`; `docs/bundle-report.md` with `tools/bundle-report.mjs` that reproduces it; `docs/design-system-feedback.md` with the consolidated findings for the design system.
- **Scripts and CI.** `build:lib` (library plus schematics) is used wherever the library is built; `snippets`, `check:snippets`, `check:themes`, `test:schematics`, `format` and `format:check` are new, and `check` as well as the CI workflow run all of them plus `e2e` and `e2e:beispiel`.
- **Skip link.** `a[zSkipLink]` renders the link "Zum Hauptinhalt springen" that `spec/guidelines/15-zustaende.md` requires and that neither the API table nor `bundle.css` covers. It carries the class `z-skip-link` and nothing else: the caller writes the text and the `href`, the target needs `tabindex="-1"`, and a dev-mode check on the first focus says so when it is missing. Hidden until focused, then a block at the top left above header, overlay and toast, in `surface-raised` with `text` (16.26:1 dark, 14.77:1 light, 17.85:1 contrast). An application could not supply this itself, see the two base rules under Changed. Documentation in [`docs/components/skip-link.md`](docs/components/skip-link.md).
- **`.z-legacy`, for the pages that are not migrated yet.** An application that adopts the library route by route has `z-root` on `<html>` and `<body>`, and `body.z-root` handed `14px/20px` down into every old page: a legacy `h2` of 27.2px without a line height of its own overlapped itself on a 20px line, and body text shrank from 16px to 14px. `.z-legacy` on the content host sets `font-size: 1rem`, `line-height: normal` and `-webkit-font-smoothing: auto`, and the six base rules that style bare elements (`box-sizing` on `*`, `font` and `color` on controls, the two link rules, the underline in running text, the focus ring) stop at it, host element included, so an old `main { width: 600px; padding: 0 24px }` stays 648px wide. Each of them is written as `.z-root X:not(:where(.z-legacy, .z-legacy *)), :where(.z-legacy) .z-root X`; both `:where()` weigh nothing, so no documented specificity changes, and the second selector is what lets a `z-root` on the container of a migrated page switch everything back on. The exclusion on the universal rule costs +14 to +18 % on a forced full style recalculation (4.2 to 4.9 ms with 4130 elements, production build). Family, colour, background and `color-scheme` stay with the application, which restates its old `body` rule on the same element. Measured on the new demo page `/muster/legacy` by `e2e/legacy.spec.ts`: the old page computes to the same 33 properties per element, at rest, hovered and focused, as the same stylesheet and markup in a document without `zenit-ui`, in all three schemes; the nested `z-root` equals a normally embedded page; dialog, menu, tooltip and toast opened from the old page are unchanged. A library component placed straight into `.z-legacy` loses the base rules (an `input[zInput]` measures 326×42px in a 300px field, a `z-spinner` 20×20px instead of 16×16px) and needs a `z-root` wrapper. A typography class on `<body>`, Material's `mat-typography` for example, ties with `.z-root` and wins by source order; it moves to the content host. `@scope` was rejected because Firefox before 146 and Safari before 17.4 are inside Angular 22's browser range, `revert` because it rolls back to the browser's stylesheet. Guide: [`docs/legacy.md`](docs/legacy.md).

### Changed

- **`loading` on `button[zBtn]` no longer sets the native `disabled`.** `spec/guidelines/15-zustaende.md` ("Lädt": "alle Buttons deaktiviert, der auslösende zeigt den Spinner") wants the triggering button to keep the focus, and a native `disabled` dropped it to `body` the moment the button started to spin. A loading button now locks the way a locked `a[zBtn]` does: `aria-disabled="true"` next to `aria-busy="true"`, its `tabindex` untouched, and click, Enter and Space swallowed in the capture phase on the host (`preventDefault` plus `stopImmediatePropagation`), so no `(click)` of the caller fires and a `type="submit"` button submits nothing. The implicit submission from Enter in a text field is a click on the form's default button in Chromium, so it is caught by the same listener; measured on the new demo form on `/grundlage` (one click reaches the button, no `submit` event). `disabled` alone keeps the native attribute, and `disabled` together with `loading` is native as well. **Behaviour change for consumers:** checks that read the native state change during `loading`: a `:disabled` selector, `button.disabled` or `matches(':disabled')` in a script or a unit test, jest-dom's `toBeDisabled()` (which only honours the native attribute), and any code that expected a loading button to leave the tab order now see an enabled, focusable button with `aria-disabled="true"`. Playwright's `toBeDisabled()` honours `aria-disabled` and still passes on a loading button; the look is unchanged, because `.z-btn[aria-disabled="true"]` already carries the 45 percent. Checks in `button.spec.ts` ("loading without the native disabled") and in `e2e/interaktion.spec.ts` ("Loading button on /grundlage"), documented in [`docs/components/button.md`](docs/components/button.md).
- **`z-hero` without `[zHeroAside]` is one column.** `bundle.css` fixes `.z-hero` at `minmax(0, 7fr) minmax(0, 5fr)` and only collapses below 900px, so a sub-page hero without a right column kept an empty 5fr track from 900px up and its heading ran at 7 of 12 of the page instead of across it. `spec/components/Hero/README.md:15` allows exactly that shape ("Unterseiten … kommen oft ohne rechte Spalte aus"), so the rule `.z-hero:not(:has(> [zHeroAside])) { grid-template-columns: minmax(0, 1fr); }` was added next to the verbatim reference block in `_werkzeuge.css`. The slot marker adds no class of its own, so the selector is the attribute; `:has()` is inside the Angular 22 baseline and the library already uses it for the sticky bar in `_grundlage.css`. A hero **with** the slot is untouched, and the lead keeps its own 52 character measure either way, so the heading fills the container while the sentence below it stays readable. Measured on the computed `grid-template-columns` of both heroes of `/werkzeuge` in `e2e/zustaende.spec.ts` ("ohne [zHeroAside] eine Spalte bei 1440px, mit Aside 7 zu 5"), documented in [`docs/components/hero.md`](docs/components/hero.md).
- **The header below 900px is one row: brand, end slot, menu button.** With a 60×40px image logo and "Login" plus "Registrieren" in the end slot the bar measured 126px at 360 and 375px, because two gaps of `space-5` pushed the end slot onto a second row although the parts add up to 282 of the 312px available, and 62px everywhere else, because an inline image made the brand 45px tall. Now: `gap: space-3`, `order: 1` on the menu button (the DOM order and with it the tab order stay), an end slot that takes the room left and wraps its own items, and `display: block` for an image in `[zBrand]`. All four end slots of the first integration measure 57px at 360, 375, 412 and 899px; two buttons that cannot fit ("Anmelden" plus "Server erstellen", 238px) stack inside the end slot at 109px instead of an accidental wrap. Demo page `/muster/kopfzeile`, `e2e/kopfzeile.spec.ts`, numbers and a logo size recommendation in `docs/components/app-header.md`, which also states that the mobile menu does not lock page scroll.
- **`ZTheme` with `storageKey: null` starts from the attributes already on the target.** An application that keeps its own preference storage writes `data-theme` and `data-accent` with its own inline script; the service used to overwrite them with its defaults at bootstrap (measured in the browser: `data-theme="dark"`, `data-accent` removed), which flashes the default scheme until the application calls `setScheme()`. Registered ids are now adopted into `scheme()` and `accent()`; an attribute that only states what `defaultScheme` resolves to is not a choice, so `'system'` stays `'system'`; unknown ids fall back to the defaults. With a storage key nothing changes, and `localStorage` is still never touched without one. The attribute only prevents the flash: the application still calls `setScheme(stored)` once at start-up, and it must not run `zenitThemeInitScript` after its own script. See "Keeping your own preference storage" in `docs/theming.md`; the JSDoc of `storageKey` and the config table say the same now.
- **`docs/migration-from-material.md`.** Section 6 has the recommended structure for migrating route by route, and the click-target warning in section 8 is corrected: header links, menu button, footer links, tabs, segment buttons, menu entries and the toast action all measure 40px at 360px.

- **`z-footer` carries its own ground.** `background: var(--bg)`, added next to the verbatim reference rule, the same way `z-app-header` already does. The reference has none there because its page ground is `--bg` already; an application migrating route by route can have a light legacy surface below `body.z-root`, where the footer's `text-subtle`/`text-muted` copy is otherwise unreadable. On a migrated page the colour is the page's own, so nothing changes: the element screenshots of `e2e/zustaende.spec.ts` and the full-page shots of `navigation` and `muster/startseite` are pixel-identical. Measured with a light `.z-legacy` island on `/muster/legacy` (`e2e/legacy.spec.ts`): `.z-footer__base` and its links already carry their own `color` (`text-subtle`, `text-muted`), so nothing inherits from the legacy surface and no `color` addition was needed; both pass 4.5:1 against the new background in `dark`, `light` and `contrast`.
- **The row menu survives on a phone.** Below 640px the reference hides every cell of a row from the third on, which also hid the menu button of a row: copying an address, restarting and deleting were unreachable at 375px, and the touch-target check passed only because a hidden button is never measured. A `[zRowAction]` now keeps its cell and its row gets a third grid column, so name and status stay as the reference has them and the action stands next to them.
- **CI runs on `windows-latest`.** The reference screenshots were recorded on Windows and their path carries no platform, while the comparison runs with zero tolerance, so the ubuntu runner would have failed every screenshot test against baselines it cannot match. No Linux baselines were invented for it.

- **`z-root` on `<html>` no longer moves the rem base.** The reference rule sets `font-size: 14px` and `line-height: 20px`, and the documented setup puts the class on `<html>` as well as on `<body>`. On `<html>` that pulled `1rem` from 16px to 14px for the whole document and overrode the size the visitor set in the browser, so every legacy style written in rem shrank by 12.5% as soon as the class was set. The two declarations now live in `.z-root:where(:not(html))`, which leaves `<html>` out and still weighs (0,1,0), exactly what `.z-root` weighed; `body.z-root` carries the class itself and keeps 14px/20px, which is what every component and the CDK overlay container inherit. The components of the library compute in px; the one `rem` in its stylesheets is the `1rem` of `.z-legacy` (see Added).
- **The link base rules no longer beat application classes.** `.z-root a` and `.z-root a:hover` weighed (0,1,1) and therefore won against every class an application can put on a link (0,1,0): a hand-written skip link came out red on red at 1.29:1, and legacy links changed colour and underline the moment `z-root` was set. They are now `.z-root :where(a)` and `.z-root :where(a):hover`, the same fix the reference already has for `:where(button, input, select, textarea)`. The values are unchanged, and the computed colour, underline and underline colour of all 299 links of the demo and all 26 of the example application are identical before and after, in `dark`, `light` and `contrast`. Three consequences for a consumer: your stylesheet has to be loaded **after** `zenit-ui.css`, because at equal specificity source order decides and not specificity (the documented `styles` order does that, and a hover needs `.yourclass:hover` against the (0,2,0) hover rule); a rule of yours at (0,1,1) such as `.app a` now also reaches plain links inside panel, alert, row, table, empty state, page-header sub, header, tabs, sidebar, stepper, toast, dialog body, tooltip and menu, but not the footer lists and no link carrying a library class; and the underline for links in running text stays at (0,2,1), so it cannot be switched off from an application stylesheet — the documented way out is to be a `.z-legacy` subtree class of its own package, not the `:not([class*="z-"])` in its selector, which also takes out a class by accident (`quiz-link`).
- **The documentation writes package specifiers for the global styles.** `zenit-ui/styles/tokens.css` instead of `node_modules/zenit-ui/styles/tokens.css`, as the `ng-add` schematic already does: the specifier is resolved through Node and therefore also works in a git worktree without its own `node_modules`, in a hoisting monorepo and under pnpm.
- **`docs/ng-add.md` explains the unit tests of a linked build.** `preserveSymlinks` reaches Vitest but cannot help while the package is external and loaded by Node, which follows the link and takes `@angular/core` from the library workspace: two Angular instances and `NG0203` in every spec. `server.deps.inline` pulls the package into the Vite graph, where the option applies; both halves are needed together, `resolve.dedupe` is the alternative, and a tarball or registry install is not affected at all.

### Fixed

- **A standing toast is no longer pushed out by a fourth one.** `ZToast` closed the oldest toast whenever a fourth arrived, including one with `duration: 0` or an action, such as "Neue Version verfügbar" with "Aktualisieren": its action was gone before anyone could use it. A toast with `duration: 0` or an action is now standing and never closed to make room; the oldest toast that is not standing gives way instead, and while every visible toast is standing the new one waits and moves in when a place is free. Three timed toasts in a row behave exactly as before.
- **The thumbnail of `z-row-main` is `aria-hidden`.** `.z-row__thumb` now carries `aria-hidden="true"`, so an `a[zRow]` or a row with `a[zRowLink]` is read as title and meta only: the initial used to be read as a stray letter in front of the title ("M minecraft-01"), and an icon or image in `[zRowThumb]` would have been read as well. The image already had an empty `alt`. What the thumbnail shows belongs as text into `meta` or `[zRowMeta]`, as [`docs/components/server-list.md`](docs/components/server-list.md) says under Accessibility. Nothing changes visually.
- **`llms-full.txt` carries the guide examples and the "Don't" notes.** `leseLeitfaeden()` in `tools/generate-llms.mjs` ended every guide section with the lookahead `(?=^##\s|\Z)`, and `\Z` is no anchor in JavaScript: it matched a literal "Z", so `## Import`, `## Examples` and `## Do / Don't` of all 46 guides stopped at their first capital Z (in `{ ZButton }`, for one) and came back empty or cut. No guide example and not one "Do not" line ever reached the file, while every class fell back to its JSDoc example. The end of input is now `(?![\s\S])`. With the Import sections read for the first time, `ZConfig` and `ZConfigAside`, which both config.md and wizard.md import, landed under the wizard's guide and lost the configurator's example; a guide now prints its example under the class it is named after (wizard.md under `ZWizard`) and a class stays with the guide that owns it. Result: 46 of 46 guides contribute their html example and 46 sections carry "Do not" with 123 notes; `llms-full.txt` grows from 219.6 to 234.2 kB, `llms.txt` stays at 11.9 kB, `keinePfade` found no new pointer. `check:llms` now asserts that every guide with an html fence under `## Examples`, counted line by line independently of the section regex, has that example in the file, so the regression cannot return silently. A guide whose own class is a service (`ZDialog`, `ZToast`, `ZTheme`, `ZLabels`) gives its html example to the component or directive it also covers (`ZDialogLayout`), and the service keeps its TypeScript example from the JSDoc; where the JSDoc example of the owning class uses a tag or an attribute the guide example lacks (`iconOnly` with `aria-label` and `a[zBtn] routerLink` on `ZButton`), both are printed, which applies to 16 classes.
- **A bound `[attr.aria-disabled]` on `button[zBtn]` and `a[zBtn]` survives.** The host binding `[attr.aria-disabled]` wrote `null` whenever the library had no lock of its own and thereby deleted a bound `aria-disabled` of the caller on every change detection run; only a static one was kept, read once through `HostAttributeToken`. The attribute is now borrowed through `leiheAttribut` from `lib/a11y/host-attribute.ts`: the library writes `"true"` only while it locks (a loading button, a locked link), holds it against a binding that keeps writing, and gives back the caller's latest value, or no attribute, when the lock goes. That covers the static case too, so the `HostAttributeToken` read is gone, and the swallowed click follows the attribute as it stands, so a bound `"true"` locks the button the way a static one did. Checks in `button.spec.ts` ("aria-disabled of the caller") and `ssr.spec.ts`.
- **A `button[zGameTile]` without a cover announced its title twice.** The cover area shows the game's name as text when there is no cover, and since the fix above it does the same when a cover fails to load. Visible text inside a button goes into its accessible name, so a screen reader read "Terraria Terraria ab 1,98 € / Monat" while `docs/components/game-tile.md` promised the short form, and a tile whose cover loaded really had it: an `alt=""` contributes nothing, which is why only the tiles without a picture were affected. `span.z-game__cover` now carries `aria-hidden="true"`, so the name is title plus price for every tile — with a cover, without one and with one that just failed — and the title is still announced, from `span.z-game__title` right below. Nothing visible changes, and no screenshot moved. Measured in the browser's accessibility tree through CDP, not in the markup, by the new case "game tiles" in `e2e/a11y-baum.spec.ts`, which compares the name of every tile of `/werkzeuge` with its title and price and checks role and `aria-pressed` with it; axe stays clean in `dark`, `light` and `contrast`.
- **`z-sticky-bar` no longer measures while it is being destroyed.** The teardown of a bar removed it from the set of living bars and then measured every bar that was left, so that the tallest stuck one could set `--z-stickybar` again. On the server that measurement is not available at all: its elements have no layout and therefore no `getBoundingClientRect`, and the application is destroyed right after rendering, so `/konfigurator` died with `TypeError: bar.getBoundingClientRect is not a function`. One bar alone never hit it, because it had already taken itself out of the set — it needed two, which is why the existing spec, with one bar and no destroy, passed. A destroy now only unregisters: the last bar removes `--z-stickybar` outright, which states the same thing without reading anything, and while bars remain the measurement is handed to the next frame, where their boxes have settled anyway. The server never reaches it, because its window has no `requestAnimationFrame` either.
- **`z-slider` no longer empties its Signal Form on the server.** The slider writes scale and value straight onto the native element and reads the value back, because the element clamps to `min` and `max` and snaps to the step. The read-back was guarded with `!Number.isNaN(…)`, and the server parses no value at all: `valueAsNumber` is `undefined` there, `Number.isNaN(undefined)` is `false`, so the guard let it through and the slider reported `undefined` to the form. That dropped the bound key out of the model, and the next binding of `[formField]` found no field any more, which Angular's error handler swallowed as `ERROR TypeError: this.field(...) is not a function` while the route still counted as prerendered: `/formulare` and `/muster/startseite` wrote a page whose sliders had silently lost their value. The guard is now `Number.isFinite(…)`, which answers the question the code actually asks — did an engine parse this into a number — and covers `undefined`, `null` and `NaN` in one. Nothing changes in a browser, where a range input always reports a finite number.
- **`button[zBtn]` no longer takes the server down.** `ZButton` built its `MutationObserver` in the constructor, unguarded, so server rendering threw `ReferenceError: MutationObserver is not defined` before the first byte of the page. That reached every page carrying a `z-app-header`, whose menu button is a `button zBtn`: each one answered 404 under SSR and a prerender exited 2. The observer is now created lazily inside the branch of the effect that locks the link, behind `typeof MutationObserver === 'undefined'`, the same way `leiheAttribut` and `ZTokenAttribut` already do it. The lock itself is unchanged and still runs on the server, so a locked `<a zBtn>` carries `tabindex="-1"` and `aria-disabled="true"` in the rendered HTML; only the re-assertion against a caller rewriting `tabindex` waits for the browser, where nothing has rewritten it yet. The other ten observer constructions in the library were audited with it and were already safe: `a11y/host-attribute.ts`, `configurator/sticky-bar.ts`, `cost-chart/cost-chart.ts` and `spinner/spinner.ts` carry the `typeof` guard, and `dialog/dialog-layout.ts`, `menu/menu.ts`, `navigation/sidebar.ts` and `table/table.ts` construct theirs inside `afterNextRender`, which never runs on the server. New spec `projects/zenit-ui/src/lib/ssr.spec.ts` renders every component of the library that owns an observer with all three observer globals stubbed away, and asserts that construction and the first change detection throw nothing and that the attributes the library owns are in the HTML.

- **An application's own `html { font-size }` wins again.** The rule that was meant to undo the
  reference's 14px/20px on `<html>`, `html.z-root { font-size: 100%; line-height: normal }`, weighed
  (0,1,1) and therefore beat every application rule on the root element, which is (0,0,1) at most.
  The first consumer put its user setting there as `html { font-size: var(--base-font-size) }` with
  14px and 18px and got 16px for both, before and after `zenit-ui.css`, because specificity decides
  before source order. The library now sets **nothing** on `<html>`: the two size declarations moved
  from `.z-root` into `.z-root:where(:not(html))`, so the application's rule is the only author rule
  there and wins at every specificity and in either include order, while `body.z-root` and every page
  container keep the (0,1,0) they had. `html:where(.z-root)` was not the fix: `:where()` adds
  nothing, so it is the tag alone at (0,0,1) and loses to `.z-root` (0,1,0) in any order (measured:
  14px). Measured against the previous build: `font-size` and `line-height` of all 774 elements of
  `/grundlage`, `/formulare` and `/muster/legacy` at 1440 are identical, and the element screenshots
  are unchanged. New in `e2e/legacy.spec.ts`: the application rule at 14px and 18px before and after
  the library stylesheet, and `1rem` inside a `.z-legacy` island following it.
- **`aria-describedby` of a field belongs to the caller too.** `input[zInput]`, `textarea[zInput]`
  and the `<select>` inside `z-select` bound the whole attribute to the hint or the error id of the
  surrounding `z-field`, so `<input zInput aria-describedby="p-eigen">` lost its own reference to
  the field's id, and a field without hint and error deleted the attribute outright. The id of the
  field is now one token in front of whatever the caller wrote, static or bound, it is removed again
  when hint and error are gone, the attribute disappears with its last token, and no token is
  written twice. A `zTooltip` on the same control adds its own id at the back, so caller, field and
  tooltip write the same attribute without deleting each other; the field keeps the front and the
  tooltip the back, so the two never push each other around. `aria-invalid` of the caller is kept
  the same way: while `invalid` holds, the library value stands, and afterwards the caller's own
  comes back. Unit tests in `projects/zenit-ui/src/lib/field/input.spec.ts` ("aria-describedby with
  three writers"), and two Chromium tests in `e2e/overlays-scroll.spec.ts` run hint, error and none
  through while a tooltip stands, with a bounded mutation count so a writer that answers its own
  record fails instead of freezing the tab.
- **`<z-segment aria-label="Ansicht">` names the group again.** The host binding wrote `null`
  whenever the `ariaLabel` input was empty and deleted the attribute the caller had written, which
  left a `role="group"` with no accessible name at all. The attribute is borrowed now: the input
  wins while it holds a value, the caller's attribute stands while it does not, static as well as
  bound. `aria-labelledby` is never written by the component.
- **`z-spinner` and `z-table-container` stop deleting attributes of the caller.** A `role` or an
  `aria-label` on `<z-spinner>` survives an empty `label`, and a spinner the caller named itself is
  no longer `aria-hidden="true"`. `<z-table-container>` borrows `role`, `tabindex` and `aria-label`
  only while the table actually overflows and gives the caller's values back when it fits again,
  instead of writing `null` over them on every resize.
- **A borrowed attribute holds against a caller's binding and gives back its latest value.** The
  first version remembered the value at borrow time and let every later write of the caller win, so
  `<z-segment [attr.aria-label]="name()" ariaLabel="Marke">` lost the input's name as soon as
  `name()` changed and got a stale one back afterwards, a `z-table-container` lost `role="region"`
  and its tab stop while it was still scrolling, and a caller that cleared its binding saw the
  deleted value resurrected on give-back. `leiheAttribut` now watches the attribute while it is
  borrowed, notes each write of the caller as the value to give back and asserts the library value
  again, the same way `button[zBtn]` holds its `tabindex` while a link is locked.
- **`z-spinner` decides from the element, not from the static attributes.** `role` and `aria-label`
  were read once at construction, when a caller's `[attr.aria-label]` had written nothing yet, so a
  bound name was silently hidden behind `aria-hidden="true"`. The question is asked of the element
  now and answered again whenever the caller writes or removes those attributes.
- **No `MutationObserver` on the server.** Both writers create their observer lazily and only where
  the global exists: `<input zInput>` inside a `z-field` with a hint writes its token during the
  first change detection run, which used to throw `MutationObserver is not defined` while rendering
  on the server. Only the re-assertion against a caller is missing there, and nothing re-asserts
  before the browser takes over.
- **One rule for host bindings on attributes a caller writes.** The three ways out are
  `leiheAttribut` (borrow a single value), `ZTokenAttribut` (own one token of a list) and
  `HostAttributeToken` (read a static attribute once), all in `projects/zenit-ui/src/lib/a11y/`;
  at most one token writer per attribute and end on one element, which a development-mode check
  enforces instead of letting two of them push a token back and forth until the tab freezes;
  `zTooltip` and the field share the token implementation instead of carrying two copies of the
  same `MutationObserver` guard. The rule for new blocks is in `CONTRIBUTING.md` under "Host
  bindings and caller attributes". With `landmark` off, `z-app-header` and `z-footer` still own
  their `role` attribute by design; a role of your own goes on a wrapper, which both guides now say.

- **A long dialog scrolls in its body instead of past the screen.** Through `ZDialog.open()` the
  limit of the reference never reached the dialog: the CDK loads the styles of `.cdk-overlay-pane`
  at runtime, so its `max-height: 100%` stood after the library stylesheet, and `max-height: inherit`
  of `.z-dialog` inherited from the host element of the opened component in between. Measured on a
  form of twelve fields at 1440×700, the dialog ended at 1163px. The limit is repeated as
  `.cdk-overlay-pane.z-dialog-panel`, container and component host pass it on as flex columns, and
  only `.z-dialog__body` scrolls: heading and actions stay. `dvh` where the browser has it and
  `env(safe-area-inset-bottom)` on the mobile footer keep URL bar and home bar off the actions. A
  body that scrolls without holding a tabbable element becomes a tab stop of its own (WCAG 2.1
  SC 2.1.1), a `role="group"` named by the heading, decided by `InteractivityChecker` and watched
  while the dialog stands.
- **Tooltip and menu answer a scroll in any container.** Both relied on `ScrollDispatcher`, which
  only hears the window and containers marked `cdkScrollable`: in the body of a scrolling dialog the
  tooltip stood still while its trigger moved away and the menu stayed open. Each listens for
  `scroll` on the document in the capture phase while it is open, and only for a scroller the trigger
  sits in, so a console that follows its own log leaves the overlays of the panel header alone. The
  tooltip goes like the native `title`, unless the trigger holds the focus: then it follows, steps
  aside while a clipping container covers the trigger and comes back with it. The menu closes and
  hands focus back to the trigger only when focus was inside it; a trigger that keeps its place in a
  sticky header keeps its menu, and the scroll that was still running when the menu opened is
  ignored until it comes to rest.
- **One Escape closes one layer.** A tooltip took the key together with the dialog behind it, and a
  menu did the same, so a form of twelve fields was lost to the key that was meant for the menu. The
  tooltip catches Escape in the capture phase of the document and the menu stops it in the bubble
  phase of its own host, both before the keyboard dispatcher of the CDK on `document.body`, and only
  while they really stand.
- **A dialog opened from a menu item returns focus to the menu trigger.** The CDK closes the menu
  with the click, so the item that was focused no longer exists when the dialog closes and the focus
  fell to `<body>`. `ZDialog` finds the trigger through the `aria-controls` of `CdkMenuTrigger`;
  `restoreFocusTo` still wins where it is given, and a target without `focus()`, which is what
  `viewChild('trigger')` on a component host yields, is dropped with a warning in the development
  build instead of silently focusing nothing.
- **The tooltip no longer overwrites `aria-describedby` of its trigger.** The id of the panel is one
  token in the list while the panel stands and is taken out again afterwards, so an input keeps the
  hint and the error that a `z-field` links to it, even while the field rewrites the attribute on
  every keystroke. The rewrite used to cost the description; answering it naively costs the tab,
  because Chromium queues a mutation record for an unchanged value as well.
- **A `tabindex` written by the caller survives `zBtn`.** The host binding evaluated to `null` for
  everything but a locked link and thereby deleted the attribute, so `<button zBtn iconOnly
tabindex="-1">` inside an input group became a tab stop. `tabindex` is only touched on a locked
  link now: the lock borrows the value, holds against a binding that keeps writing, and gives the
  last value back when it goes.
- **The package loads without AOT linking.** `ZTableContainer` queried `ZTable` and `ZWizard` queried `ZWizardStep` before those classes were declared. A signal query's predicate is part of the static partial declaration, so a consumer whose unit tests load the package unlinked (the Vitest runner of `@angular/build:unit-test` keeps packages outside the test bundle, with or without `aot: false`) got `ReferenceError: Cannot access 'ZTable' before initialization` from every spec that imports anything from `zenit-ui`. Application builds were never affected. The classes are reordered, no API changed. New gates so it cannot return: `npm run check:order` (source scan with file and line, plus import cycles), `npm run check:bundle` (imports the built bundle in plain Node with the JIT compiler) and `npm run test:beispiel:jit` (the example application's specs against the unlinked package), all part of `npm run check` and CI.
- **Tooltip stays open while the pointer is on it** (WCAG 2.1 SC 1.4.13): the overlay no longer closes when the pointer moves from the trigger onto the tooltip, and its text updates while it is open.
- **Slider keeps model and track on one value**: a clamped value is written back to the input, so thumb, fill and model cannot drift apart.
- **Toasts are announced**: the outlet holds two permanent live regions, `role="status"` with `aria-live="polite"` for neutral and success and `role="alert"` with `aria-live="assertive"` for danger, instead of creating a region together with its message.
- **Pagination**: `pageSize` is clamped, the pager names its landmark and the focus stays on the button that was pressed.
- **Console** log has `role="log"` instead of a live region that reads every line out loud, and a `table[zTable]` gets a focusable overflow region only where it actually scrolls.
- **Explicit `type="button"`** on every button the library renders, so no button inside a form submits it by accident; the sidebar keeps its label in sync.
- **Form controls write to the DOM**: `writeValue()` and `model()` reach checkbox, toggle and slider.
- **Published types are clean**: `@Service()` for the root singletons, `stripInternal` so internal types stay out of the `.d.ts`, and a cheaper label sync.
- **Error frame for the native `<select>`**: `aria-invalid="true"` colours the border of a select the same way it colours the border of an input.
- **The mobile header menu closes itself.** Below 900px `z-app-header` kept the open menu standing over the page a projected link had just loaded, and the state was private. `open` is now a `model(false)`, bound as `[(open)]`; a click on a link inside the `<nav>` closes the menu (delegation over `<a>`, so no `@angular/router` in the library, and a button inside the nav leaves it open), and Escape inside the header closes it and returns the focus to the burger button.
